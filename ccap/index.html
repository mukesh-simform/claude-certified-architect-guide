    How to read a scenario question

    A scenario question usually stresses one constraint: control, audience, cost, latency, risk, compliance, or reliability. Options often name a trade-off. Several options are true statements. Only one answers the constraint the scenario stresses, and usually with the smallest change that fixes it. Three eliminations work on most items:

    • Bigger model, more tools, more autonomy is rarely the answer to a reliability, cost or risk problem.
    • Monitor it, log it, or add a confirmation loses to removing the risk when removal is possible.
    • Fix the root cause at its layer: stale data is a retrieval problem, a broken rule is a determinism problem, a wrong format is a prompt or schema problem.

    High-yield: the most-confused concepts

    These four topics have the most moving parts and are the easiest to mix up. Give them extra time on Day 1.

    1. Cache invalidation by prefix level (Domain 2 §5). A change breaks its own level and everything after it, never above.
    2. Tool search round-trip (Domain 3 §1). Never defer the search tool; resend every tool each turn; expansion is automatic; no tool_result for srvtoolu_.
    3. Metric families (Domain 4 contrast box). Wording, meaning, fields or judged quality decides the grader.
    4. Subagents, agent teams, dynamic workflows (Domain 1 §4b). Who talks to whom, what it costs, the hard limits.

    2. Decompose: give every step the right owner

    OwnerOwns
    ClaudeLanguage work: reading, extracting, summarizing, drafting, planning, tool-mediated action.
    Existing systemsRules, records, live state and exact calculation: rule engine, order system, database of record, policy tables.
    HumansApprovals, judgment calls, exceptions, anything high-stakes or irreversible.

    Test each step for reversibility, stakes and accountability. Ask "where do Claude's properties argue for Claude over the system that already does this?" A claims assistant: Claude reads the claim; the rule engine decides priority; coverage comes live through a tool or MCP; Claude drafts the email, the email system sends it, and a human approves above a value threshold.

    • Fixed, known steps → prompt chain. Subtasks only knowable at run time → orchestrator-workers.
    • Split along one axis: by stage (extract, check, draft), section (chapter, file), perspective (legal, financial) or specialism (tool or model).
    • Attention dilution (the "lost in the middle" effect): one pass over a long input misses items in the middle. Run a pass per unit, then an integration pass that reconciles and de-duplicates. Both are needed.
    • Use schema'd intermediate outputs with a check between steps. Don't split work that fits comfortably in one call.
    Trap · deterministic drift

    A "claims over $5,000 go to a senior adjuster" rule was moved into a prompt. 41 of 14,000 claims were misrouted, all with amounts written as text ("around five thousand dollars"), and nothing logged the model's choice. Let Claude extract the amount into a field. Keep the threshold in the rule engine.

    The building block of every pattern is the augmented LLM: a model with retrieval, tools and memory. Workflows follow predefined code paths; agents direct their own process and tool use. Agents in production always have constrained tools, turn budgets, permissions and stop criteria.

    Workflow patternHow to recognize it in a stem

    Trap · flexibility mistaken for need

    A team picked an agent because the task "felt open-ended". Traces later showed only four real paths. A router plus four chains would have been cheaper, testable and auditable. They had also added so many guardrail tools that they had rebuilt a workflow inside the agent, without the logging.

    Quality ladder: improve the prompt, then add tools or retrieval, then a stronger pattern (evaluator-optimizer), and only then fine-tuning (very high volume, tight latency, or a format prompting cannot hold).

    4. Multi-agent: orchestrator and subagents

    The orchestrator owns the goal, splits work, delegates and synthesizes, and never does sub-task work. Subagents each run one scoped unit in a clean context. Fan-out over a large item (400 files, 200 documents, 50 rules) gives clean contexts and concurrency. Budget for cost: Anthropic measured agents at about 4× the tokens of a chat and multi-agent systems at about 15×, so multi-agent must buy something a single agent can't.

    Orchestrator loses goal or stateUsually notProtect and checkpoint orchestrator state; make subagent work idempotent

    Trap · the dropped unit

    A 50-section contract review reported "48 sections reviewed, 3 flagged". Two subagents had failed silently, and the fluent summary hid the gap. Reconcile dispatched units against returned results before synthesis, and state coverage in the output.

    Course versus current docs

    The course teaches the three-tier family as Opus (most capable), Sonnet (default start) and Haiku (fast, cheap). Current docs add Fable at the top and recommend starting with Opus 5.5. The principle tested is the same: start at the balanced default, then move up or down only on eval evidence. If a question offers only Opus, Sonnet and Haiku, the course answer is to start on Sonnet.

    Requirement first, lever second, model last. "Accuracy outweighs cost" for autonomous work points to the most capable model. "Replies are too long" is an output-control problem: lower effort, prompt for brevity, cap max_tokens. It is never fixed by a smarter model.

    Move models on evidence, never by reflex. Build a stratified eval set, set the rollback criterion before the data comes in, and compare per segment. In the course case Sonnet scored 0.94 and Haiku 0.86 on average. Two document types fell to 0.71 and 0.74, under the pre-set 0.85 floor, so the full migration was rejected. Routing those two types to Sonnet and the rest to Haiku still cut cost. Routing by difficulty is often the best answer.

    Thinking adds a billed reasoning pass, charged as output tokens, and adds latency. Use it for multi-step reasoning, not for simple lookups. Current models use adaptive thinking: Claude decides whether and how much to think, steered by output_config.effort. On the current models the manual mode (budget_tokens) returns a 400. Opus 5.5 can't turn thinking off (disabled returns a 400 at every effort level), so effort is the control. Sonnet 5.5 also rejects disabled; to turn thinking off, send thinking: {type: "between_tools"} (effort high or below). Fable 5.1 thinking is always on. Assistant-message prefill returns a 400 on current models, so control format with structured outputs or instructions. Non-default temperature, top_p and top_k are rejected on Claude 4.7 and later models (and from API version 2026-10-21, sending them at all is a 400 on every model). Changing thinking or effort between requests invalidates cached messages, so keep them stable on cached conversations.

    Thinking blocks across turns. Inside a tool-use turn, pass thinking blocks back complete and unmodified with the tool_result. Once a new user message that is not a tool result arrives, older models (earlier Opus and Sonnet, and Haiku 4.5 and before) strip all previous thinking blocks: they stop counting toward context, while text, tool_use and tool_result stay. Current models (Opus 4.5 and later, Sonnet 4.6 and later, Haiku 5.5, Fable and Mythos) keep prior-turn thinking. History is not always append-only. Extended thinking

    4. Context windows and tokens

    • The context window is a hard edge. Outside it the model has no access. Everything counts toward it: system prompt, history, retrieved documents, tool results and outputs.
    • Measure with the usage field and the token-counting endpoint. Never assume a characters-per-token ratio.
    • Window sizes: 1M tokens on all four current models (Fable 5.1, Opus 5.5, Sonnet 5.5, Haiku 5.5), with up to 128K output. 200K on older models such as Sonnet 4.5 and Haiku 4.5. Tool definitions and thinking also count, and cached tokens still occupy the window.
    • Overflow: input alone too long gives 400 invalid_request_error ("prompt is too long"). Input fits but input plus max_tokens exceeds the window: on Claude 4.5 and newer the request is accepted and stops with stop_reason: model_context_window_exceeded (older models return a validation error). A request body over the API's size limit is rejected separately from the token limit.
    • Built-in context management: server-side compaction summarizes older turns in long conversations (the docs' main strategy for long agentic work); context editing clears old tool results or thinking blocks in agent loops; the memory tool keeps facts outside the window across sessions ("resume tomorrow").
    • The model has no memory between calls. Continuity comes from what your app stores and sends back. Live data needs a tool call.
    • Quality can degrade on very long contexts before the limit. Put long documents first and the question last, and trim what the step does not need.

    5. Reuse: caching, modular prompts, Skills

    LeverRule
    Prompt cachingCaches a stable prefix. Static content first, dynamic last, breakpoint between them. Cuts cost and time to first token on repeated prefixes. Pick the cache lifetime by call frequency; infrequent calls or small prefixes may not repay the cache write.
    Caching numbers
    • Lifetime 5 minutes by default (write 1.25x input price) or 1 hour (write 2x). Each reuse refreshes it at no cost.
    • Read 0.1x by default (Sonnet 5.5 included: $0.20 on $2 input), 0.05x on Opus 5.5 ($0.20 on $4), 0.025x on Fable 5.1 ($0.25 on $10). A shorter lifetime never lowers the per-token price.
    • Up to 4 breakpoints. Automatic caching (one top-level cache_control) uses one of them, leaving 3 explicit slots.
    • Each breakpoint looks back at most 20 block positions. Long conversations need explicit breakpoints so earlier entries stay in range.
    • Minimum cacheable prompt: 512 tokens on current models, up to 4,096 on older ones such as Haiku 4.5. Below the minimum the prompt is silently not cached, with no error.
    • Order is tools → system → messages. A change invalidates its own level and everything after it, never above. Tool definitions: all three. Web search, citations or speed: system and messages. tool_choice or images: messages only, so cached tools and system still hit. (Forced tool_choice, any or tool, returns a 400 on Opus 5.5, Sonnet 5.5 and Fable 5.1; there the choice is between auto and none.) Thinking or effort: messages always, and tools and system too on models that render the thinking config ahead of them. Judge a parameter by where it sits in the prefix, not by its name.
    • Cache hits don't count against input-token rate limits, so caching also raises throughput.
    Modular prompt libraryAssembled, often-tweaked fragments owned by engineers in one codebase or team.
    SkillsPackaged, stable procedures (instructions, scripts, resources) reused across teams and products with versioning, approval and rollback. Progressive disclosure in three levels: name and description always loaded (about 100 tokens each), the SKILL.md body when triggered (under 5K tokens), bundled files and scripts only when used. Use Skills only from trusted sources, since they can direct tool use and code execution. Custom Skills do not sync between the API, Claude.ai and Claude Code. SKILL.md frontmatter: name up to 64 characters (lowercase letters, numbers, hyphens; may not contain "anthropic" or "claude") and description up to 1,024 characters. Claude sees only these until the skill triggers, so the description must say what it does and when to use it. On the API, custom Skills need the code execution tool and are shared across the workspace.

    Integration

    19% · ~12 items15 min read

    1. Capability bloat and least privilege

    Every tool an agent holds is attack surface, selection noise and context tokens. Give each role only the tools that role needs.

    • Remove tools the role does not need. That beats logging them, adding confirmations, or hoping the prompt prevents misuse. Removing a capability beats guarding it.
    • Prefer narrow, single-purpose tools (get_order_status) over broad ones (run_sql). Split read tools from write tools, and gate write or irreversible tools behind human approval.
    • Too many similar tools reduce selection accuracy: Anthropic's docs say accuracy degrades beyond roughly 30–50 tools. Write clear, distinct, namespaced names (github_, slack_) and descriptions with typed parameters, and return concise, structured results.
    • With large catalogs (10+ tools or 10K+ tokens of definitions, common with several MCP servers), use the tool search tool: mark tools defer_loading: true so only the 3–5 needed load per request. Docs cite over 85% fewer definition tokens. Keep the few most-used tools always loaded.
    • Two variants: tool_search_tool_regex_20251119 (Claude writes regex patterns; best for strict, consistent prefixes such as db_read_, db_write_) and tool_search_tool_bm25_20251119 (natural-language queries; best for descriptive or inconsistent names). At least one tool must stay non-deferred, or the request returns a 400; never set defer_loading on the search tool itself, since it is the only way to reach deferred tools. Both variants match tool names, descriptions, argument names and argument descriptions, case-insensitive; a regex pattern is capped at 200 characters and a BM25 query at 500. A deferred tool cannot also carry cache_control (400 error); put the breakpoint on a non-deferred tool. Up to 10,000 deferred tools per request; each search returns up to 5 tools by default.
    • Continuing the conversation. The search runs server-side as a server_tool_use with an srvtoolu_ id: never send a tool_result for it, or the request is rejected. The result holds tool_reference blocks that the API expands into full definitions automatically; you never inject schemas. Claude then calls the discovered tool as a normal toolu_ call, which you run and answer. Every later request resends the whole tools array, deferred tools included, plus the prior assistant content unchanged. Tool search tool
    • Don't use tool search with fewer than about 10 tools, when every tool is used on every request, or when definitions are tiny.

    5. RAG pipeline: chunk, index, retrieve

    ChoiceOptionPick when
    Chunking (by corpus structure)Fixed-size with overlapHomogeneous, unstructured text; simplest
    SemanticProse where each chunk must stand alone
    HierarchicalContracts, manuals, policies where the section carries meaning
    Indexing (by query pattern)Dense embeddingsParaphrase, intent, concepts
    Sparse (BM25)Exact tokens: part numbers, error codes, statute citations
    Hybrid, merged by reciprocal rank fusionMixed queries, the usual production case

    Add a reranker after broad retrieval to improve precision. Prepend a short (about 50–100 token) document-level context to each chunk before embedding and BM25 indexing (contextual retrieval) so isolated chunks keep their meaning. Anthropic measured retrieval failures down 35% with contextual embeddings, 49% adding contextual BM25, and 67% adding a reranker. Contextualized chunk embedding models (Voyage voyage-context-*) do this inside the embedding. The current one is voyage-context-4 (voyage-context-3 is the previous generation), called through contextualized_embed(). When a stem wants each vector to carry document context automatically, this beats wider chunk overlap, which only adds neighboring sentences. Use metadata filters (date, product, region, permissions) to scope results. Retrieval must respect the user's document permissions.

    Practical RAG rules
    • Small corpus, no RAG. Under about 200K tokens (about 500 pages) of stable knowledge, put it all in the prompt and cache it.
    • Retrieve broad, rerank narrow. Anthropic's reference setup retrieves the top 150 chunks and reranks to the top 20.
    • Filter before ranking. Apply metadata and permission filters in the query, not on the results.
    • Refresh atomically, pin the embedder. Re-chunk, re-embed and swap the whole index in one step, with one pinned embedding model version. Vectors from two embedding models don't match; this is a common cause of "confident but wrong after a refresh".
    • No universal chunk size. Pick by structure, then tune size and overlap on your own retrieval eval (recall at k).

    Evaluation, Testing & Optimization

    16% · ~10 items12 min read

    1. Metrics: define all five before building

    Accuracy and qualityTask success, exact or field match, groundedness, rubric score, citation correctness.
    LatencyTime to first token, p50/p95/p99 end to end, per step.
    CostTokens and cost per completed task, cache hit rate.
    SafetyHarmful-output rate, policy violations, correct refusals versus over-refusals.
    SecurityPrompt injection resistance, data leakage, unauthorized tool calls.

    Make success criteria specific and measurable ("≥95% field accuracy on the golden set, p95 under 3 s"), not "works well". Write them before you build the eval.

    Success criteria: SMART

    LetterMeansFails like
    SpecificNames the task and the quality dimension"Good summaries"
    MeasurableA number, a threshold, a sample size and a defined grader"A manager signs off on each summary"
    AchievableGrounded in benchmarks, prior experiments or industry results"100% accuracy on open-ended answers"
    RelevantTied to the business outcomeA metric users never feel

    The docs list these four. Some study material adds Time-bound (a date or release gate). The docs' model criterion: "F1 score of at least 0.85" on a stated held-out test set.

    The prompt engineering cycle

    Success criteria→Test cases→Draft prompt→Test and refine (loop)→Final validation on held-out cases→Ship

    The step after "has test cases and a draft" is always test against the cases and refine, not final validation. A variant that wins after many revisions on one set must be confirmed on a held-out set before you trust it.

    2. Datasets and mixed methods

    • Golden set: representative real inputs with validated expected outputs, stratified by segment (document type, intent, language) so per-segment scores mean something.
    • Add edge cases, adversarial cases (injection, jailbreak, out-of-scope) and regression cases from every production bug.
    • Keep refreshing from production samples so the set keeps up with real traffic.
    • Report scores with confidence intervals and compare variants on the same cases (paired). A 2-point gap on 50 cases is usually noise; grow the set before deciding.
    GraderBest forWatch for
    Code-basedExact match, schema validity, field accuracy, test pass, latencyCan't judge tone or nuance
    LLM-as-judgeTone, helpfulness, groundedness, rubric criteria at scaleCalibrate against human labels; use clear rubrics; judge bias
    Human reviewGround truth, high-stakes, calibrationSlow, expensive; use for samples and disagreements

    Use the cheapest reliable grader per criterion. Mixed methods means combining all three. The docs say automate when possible: many cases with automated grading beat a few hand-graded ones. For an LLM grader, give a clear rubric, ask for a binary yes/no or a 1–5 score with labeled ends, ask for the score only, and use a different model from the one being graded.

    3. A/B testing and iteration

    • Offline eval first, then online A/B on live traffic.
    • Change one variable at a time (prompt, model, retrieval setting) with a fixed eval and success metric chosen in advance.
    • Run until the sample is large enough to be meaningful. Track guardrail metrics (cost, latency, safety) so a quality gain cannot hide a regression.
    • Version prompts like code. Every change runs the regression suite in CI before release, and a canary or gradual rollout comes with a rollback plan.
    • Stage exposure: offline eval → shadow (new version runs on live inputs, output and actions discarded) → canary (small share of traffic) → A/B → full rollout. A rollback plan doesn't replace staged exposure.

    Sampling settings are not a fix either. Current models (Claude 4.7 and later) reject non-default temperature, top_p and top_k, and even on older models that accept it, temperature 0 is not deterministic and doesn't fix hallucination.

    5. Optimize cost, latency and tokens

    • Prompt caching for repeated prefixes. Static content first (see the Domain 2 worked scenario).
    • Route by difficulty: small model for simple steps, larger only where the eval proves the need.
    • Batch processing for non-urgent bulk work.
    • Trim context: retrieve less but better, compact history, drop unused tool definitions.
    • Cap output: concise output instructions, sensible max_tokens, structured formats.
    • Never cut required context (such as truncating the policy) or pick a model that does not fit the task just to save money.

    Dashboards for latency percentiles, error and stop-reason mix, tokens and cost per task, cache hit rate, tool error rate, and sampled quality scores. Alert on change from baseline. Each incident becomes a regression test.

    5. Ethics: bias, fairness, transparency

    • Bias and fairness: evaluate quality and outcomes per demographic or user segment. Remove protected attributes, and proxies for them, from decision inputs where they are not needed. Keep consequential decisions (credit, hiring, care) under human review.
    • Transparency: tell users they are dealing with AI, show sources and citations, explain the basis of recommendations, and offer an escalation to a human.
    • Accountability: a named owner for each system, documented intended use and limits, and an audit trail of model and prompt versions per decision.

    2. Communicating decisions and trade-offs

    • Write Architecture Decision Records: context, decision, options considered, trade-offs, consequences, and the conditions for revisiting.
    • Speak in the stakeholder's terms: executives hear cost per task, risk and time to value; engineers hear latency, interfaces and failure modes; compliance hears data flows and controls.
    • Present options with explicit trade-offs and a recommendation, backed by eval numbers, not opinions.
    • Be clear that outputs are probabilistic. Commit to measured rates on an eval set, never "it will always be right".

    3. Expectations, feedback loops and SLAs

    SLA elementMake it measurable as
    QualityAccuracy or rubric score at or above a threshold on an agreed, versioned eval set
    Latencyp95 (and time to first token for chat) under a stated bound at stated volume
    AvailabilityUptime target, plus fallback behavior when the model or a tool is unavailable
    EscalationShare of cases routed to humans, and human response time

    Final review

    Use this chapter after you have read the domains and drilled the contrast boxes. Detailed settings are rarely worth memorizing; scenario items reward knowing which layer a control lives in and which control is the smallest fix.

    Five questions to ask of every item

    1. Constraint. Which one is stressed: cost, latency, risk, compliance, reliability, control, audience?
    2. Layer. Where does the problem live: prompt, model, retrieval, tool, permissions, infrastructure, process?
    3. Smallest fix. What is the least change that solves it at that layer?
    4. Remove or watch. Can the risk be removed, or does the option merely monitor it?
    5. Exact feature. Does the option name the real mechanism for this noun (grader type, cache setting, permission control), or a near neighbor?

    Elimination rules

    Absolutes"Always", "never", "guarantees" and "100%" are usually wrong for probabilistic systems.
    Drastic fixesRe-architecting, fine-tuning or switching model when a configuration change would do.
    More of XMore tools, agents, autonomy or context is rarely the cure for reliability or cost.
    Wrong metricAn average where a percentile is needed, or similarity where exact match is needed.
    Over-engineeringMachinery without the scale or reuse that would justify it.
    Layers beat one controlDefense in depth beats a single instruction or filter.
    Batch only when nobody waitsAny interactive requirement rules it out.
    Match the setting to the nounAn org-level problem needs an org-level control; a session problem, a session control.
    Read qualifiers twice"First", "least", "most cost-effective" and "select two" change the answer.
    Multi-selectRule out the clearly wrong options first, then judge each remaining option on its own.

    Exam-day pacing and tactics

    • Budget about 90 seconds per item on the first pass. Flag anything slow and move on.
    • Keep about 25 minutes at the end to revisit flagged items.
    • Check how many answers a multiple-response item wants before reading the options.
    • Change an answer only when you can name the specific reason, such as a qualifier you missed.
    • When two options both work, choose the simpler, more deterministic, more measurable one.
    • Unfamiliar setting names are normal. Reason from the concept and from which layer the control belongs to.

    Self-check scenarios

    Original practice scenarios. Answer in your head, then open the reveal.

    A support assistant gives correct but overlong replies and the length limit keeps being breached. What is the cheapest first change?

    Prompt for brevity, set a maximum output length, or lower effort. Changing model family is the heavier fix and does not target length.

    An agent was given a list of pre-approved read-only tools, yet it edited files while running in bypass mode. Why, and what fixes it?

    A pre-approval list approves those tools without a prompt; it does not forbid the others, and bypass approves everything else. Add deny rules or a blocking hook, and avoid bypass for this agent.

    In a long chat the cache hit rate drops late in the conversation although the system prompt is marked for caching. What is the likely cause?

    A breakpoint looks back at most 20 block positions. Add explicit breakpoints as the conversation grows.

    The requirement is that 95% of replies arrive within two seconds. Which latency measure do you track?

    The 95th percentile. An average hides the slow tail.

    A classifier must return one of five fixed labels. How do you grade it?

    Exact match against the expected label. An LLM grader adds cost and noise with no benefit.

    A 400-person organization sees 429 errors, while one small team's own usage is light. What should you look at?

    Rate limits are shared at the organization level. Review total demand, per-user allocation, caching, batching for non-urgent work, and request a higher limit if needed.

    A clinic wants to run overnight summarization of patient notes through the bulk batch endpoint. What do you check first?

    Whether that feature is covered by the organization's HIPAA arrangement. The Batch API is not HIPAA-eligible, and a request using an ineligible feature returns a 400. Run it through the Messages API instead.

    A developer signed in with a subscription but sees API usage charges. Where do you look?

    An API key set in the environment overrides the login. Unset it and check the status screen.

    An agent with 300 connected tools keeps choosing the wrong one. What helps?

    Trim tools per role and use tool search with deferred loading so only relevant definitions are loaded.

    Security says a destructive command must never run, even when a developer approves everything automatically. Which control?

    A deny rule or a blocking pre-tool hook, since those are evaluated before the permission mode can approve.
