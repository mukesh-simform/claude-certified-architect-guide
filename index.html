Task 1.1
The Agentic Loop Lifecycle

The agentic loop is the core execution model: Claude receives a message, reasons about what to do next, calls tools, receives results, and continues until the task is complete. The loop is controlled entirely by inspecting stop_reason.

How the loop works

# Pseudocode — works the same in Python and TypeScript
messages = [{"role": "user", "content": user_task}]

while True:
    response = client.messages.create(
        model="claude-opus-4-6",
        tools=tools,
        messages=messages
    )

    if response.stop_reason == "end_turn":
        break  # Claude is done — return final text

    if response.stop_reason == "tool_use":
        # 1. Append Claude's response (with tool_use blocks) to history
        messages.append({"role": "assistant", "content": response.content})

        # 2. Execute each requested tool
        tool_results = []
        for block in response.content:
            if block.type == "tool_use":
                result = execute_tool(block.name, block.input)
                tool_results.append({
                    "type": "tool_result",
                    "tool_use_id": block.id,
                    "content": result
                })

        # 3. Append tool results — Claude reads these on next iteration
        messages.append({"role": "user", "content": tool_results})

The two stop_reason values you must know

stop_reasonMeaningAction
"tool_use"Claude wants to call one or more toolsExecute tools, append results, loop again
"end_turn"Claude is done — final answer in contentBreak the loop, return text to user
Exam Traps — Anti-Patterns

The exam tests that you know what NOT to do. Never check for natural language signals like "I'm finished" to stop the loop — use stop_reason. Never use an arbitrary iteration cap as your primary stopping mechanism (a safety cap is fine, but end_turn must be the primary terminator). Never check for assistant text content as a completion indicator.

Why tool results go into conversation history

Claude has no side-channel to receive tool results — they must be appended to the messages array as a user turn with tool_result blocks. This is how Claude's reasoning context grows: every tool result is visible in subsequent turns, allowing it to reason about what it discovered.

Key Distinction — SDK vs. Client Library

With the Anthropic Client SDK you implement the tool loop manually (the code above). With the Claude Agent SDK (claude-agent-sdk), the SDK handles the loop internally — you just call query() and iterate over yielded messages. Both architectures use the same underlying stop_reason logic; the SDK just abstracts it.

Task 1.2 & 1.3
Multi-Agent Orchestration: Coordinator–Subagent Pattern

Multi-agent systems use a hub-and-spoke (coordinator–subagent) architecture. One coordinator agent owns all routing decisions, error handling, and information flow. Subagents are specialized workers that receive explicit context in their prompts.

Architecture overview

COORDINATOR AGENT
Task decomposition · Routing · Result aggregation · Error handling
Web Search
search tools only
Doc Analysis
read tools only
Synthesis
structured output
Report Gen
write tools only

Critical rules about subagent context

  • Subagents do NOT inherit coordinator context automatically. Every piece of information a subagent needs must be explicitly included in its prompt.
  • Pass structured data to subagents — separate content from metadata (source URLs, document names, page numbers) to preserve attribution through synthesis.
  • To spawn parallel subagents, emit multiple Task tool calls in a single coordinator response — not across separate turns.

The Task tool — enabling subagent spawning

The Task tool is the mechanism for spawning subagents via the Claude Agent SDK. The coordinator's allowedTools must include "Task". The coordinator's prompt should specify research goals and quality criteria — not step-by-step instructions — to let subagents adapt.

Common coordinator failure modes

❌ Overly Narrow Decomposition
  • Coordinator breaks "AI in creative industries" into only visual arts subtasks
  • Subagents succeed at their assigned tasks — root cause is what they were assigned
  • Result: systematic coverage gaps the synthesis agent cannot fix
✓ Broad Adaptive Decomposition
  • Coordinator analyzes the full topic scope first
  • Assigns distinct, non-overlapping subtopics across all relevant domains
  • Uses iterative refinement: evaluates synthesis output for gaps and re-delegates
Exam Insight

When a multi-agent system produces correct but incomplete output, the exam consistently traces this to the coordinator's task decomposition — not to any individual subagent. Subagents working correctly within their assigned scope will not detect or compensate for gaps in that scope.

AgentDefinition — configuring subagent types

In the Claude Agent SDK, each subagent type is declared as an AgentDefinition. This is how you assign descriptions, system prompts, and tool restrictions per role — ensuring each subagent only has access to what it needs.

# Python — AgentDefinition per subagent role
from claude_agent_sdk import AgentDefinition

web_search_agent = AgentDefinition(
    name="web_search",
    description="Searches the web for current information on assigned topics",
    system_prompt="""You are a research specialist. Search for information on the
assigned topic. Return structured findings with: claim, source_url,
publication_date, and confidence level.""",
    allowed_tools=["WebSearch", "WebFetch"]   # ONLY search tools
)

synthesis_agent = AgentDefinition(
    name="synthesis",
    description="Synthesizes research findings into coherent reports",
    system_prompt="""You receive structured findings from other agents.
Combine them into a coherent report. Preserve all source attributions.
Flag conflicts between sources with both values included.""",
    allowed_tools=["verify_fact"]  # scoped cross-role tool only
)
Key AgentDefinition Rules

system_prompt defines the subagent's persona and task-specific instructions. allowed_tools is the enforcement mechanism — not the description. A synthesis agent with allowed_tools=["WebSearch"] will misuse web search even with a good description. Restrict at the tool level, not just the prompt level.

fork_session and session branching

Use fork_session to create independent branches from a shared analysis baseline — useful for comparing two testing strategies or refactoring approaches without re-running the exploration phase. Each fork has its own isolated context from the fork point forward.

Task 1.4 & 1.5
Hooks, Enforcement, and Handoff Patterns

Programmatic vs. prompt-based enforcement

This is one of the most exam-tested concepts in Domain 1. When a workflow requires guaranteed compliance — e.g., identity verification must happen before financial operations — prompt instructions alone are insufficient. LLMs are probabilistic; there is always a non-zero failure rate.

MechanismComplianceUse When
Prompt instructions / few-shotProbabilistic (~95-99%)Guidance, best-practices, style
Programmatic prerequisitesDeterministic (100%)Security gates, financial operations, identity verification
Hook interceptionDeterministic (100%)Business rule enforcement, data normalization

Hook patterns (PostToolUse & PreToolCall)

# PostToolUse hook — normalize heterogeneous data before the model sees it
def post_tool_use_hook(tool_name, tool_result):
    if tool_name == "get_customer":
        # Normalize: Unix timestamp → ISO 8601, status code → human label
        tool_result["created_at"] = unix_to_iso(tool_result["created_at"])
        tool_result["status"] = STATUS_MAP.get(tool_result["status"], "unknown")
    return tool_result

# PreToolCall interception — block policy-violating actions
def pre_tool_call_hook(tool_name, tool_input):
    if tool_name == "process_refund":
        if tool_input["amount"] > 500:
            # Block and redirect to human escalation
            return {"blocked": True, "reason": "Exceeds $500 threshold — escalate"}
    return {"proceed": True}

Structured handoff summaries

When escalating to a human agent who lacks access to the full conversation transcript, the agent must compile a structured handoff including: customer ID, root cause analysis, amounts involved, what was attempted, recommended action. Vague escalation messages ("customer is unhappy") fail in production.

Task 2.1
Writing Effective Tool Descriptions

Tool descriptions are the primary mechanism LLMs use for tool selection. A minimal description like "Retrieves customer information" is insufficient when you have similar tools. The model has no other signal to differentiate between tools with overlapping descriptions.

Anatomy of a good tool description

❌ Weak Description
  • get_customer: "Retrieves customer information"
  • lookup_order: "Retrieves order details"
  • Both accept similar ID formats
  • No boundary explanation, no examples
✓ Strong Description
  • get_customer: "Use when you have a customer email/phone. Returns account profile. Use BEFORE any order operations."
  • lookup_order: "Use when user provides an order number (#12345). Returns shipping, items, status. Input: order_id string."

What every tool description should include

  • Purpose: what exactly this tool does (not just a noun label)
  • Input format: types, examples, constraints
  • Output: what the tool returns
  • Boundary condition: when to use it vs. similar alternatives
  • Example trigger queries: 1-2 example user inputs that should route here
Also Check Your System Prompt

Keyword-sensitive instructions in system prompts can override well-written tool descriptions. If you instruct "always verify the customer first," this may cause the model to call get_customer even for pure order queries. Review system prompts for unintended tool selection bias.

Splitting vs. consolidating tools

A generic analyze_document tool should be split into purpose-specific tools: extract_data_points, summarize_content, verify_claim_against_source. Each has a clear input/output contract. Similarly, rename overlapping tools: analyze_content → extract_web_results to remove ambiguity at the naming level.

Task 2.2
Structured Error Responses for MCP Tools

Generic error messages like "Operation failed" prevent the agent from making intelligent recovery decisions. Errors must be structured so the agent knows what type of failure occurred and whether to retry.

The MCP error structure

# MCP tool returning a structured error
return {
    "isError": True,          # MCP standard flag
    "errorCategory": "transient",  # transient | validation | permission | business
    "isRetryable": True,
    "message": "Order service timed out after 5s. Last attempt: 2026-06-01T10:30Z",
    "attemptedQuery": "order_id=ORD-12345",
    "partialResults": None
}

Error categories and how agents should respond

CategoryisRetryableAgent Action
transient (timeout, service unavailable)trueRetry with exponential backoff, or escalate after N attempts
validation (bad input format)falseCorrect input and retry, or ask user for clarification
permission (access denied)falseEscalate, do not retry
business (policy violation: refund > limit)falseCommunicate policy to user, redirect to human
Empty Results ≠ Error

A search returning zero results is a successful operation — not an error. The agent must distinguish: "the query ran and found nothing" vs. "the query failed to run." Conflating these causes the coordinator to make wrong recovery decisions (e.g., retrying a successful empty-result query).

Subagents should implement local recovery for transient errors. Only propagate errors to the coordinator when local recovery fails — and when propagating, always include: what was attempted, partial results obtained, and potential alternative approaches.

Task 2.3
Tool Distribution & tool_choice

Principle of least-privilege tooling

Giving an agent too many tools (e.g., 18 instead of 4–5) degrades tool selection reliability. More choices = more decision complexity = more misrouting. A synthesis agent should not have access to web search tools — it will use them inappropriately.

tool_choice configuration

ValueBehaviorUse When
"auto"Model may call a tool or return textGeneral use — model decides what's needed
"any"Model MUST call a tool (any one)When you need structured output and any schema works
{"type":"tool","name":"X"}Model MUST call the named toolForce a specific tool first (e.g., extract_metadata before enrichment)
# Force extract_metadata before any enrichment steps
response = client.messages.create(
    tools=[extract_metadata_tool, enrich_tool],
    tool_choice={"type": "tool", "name": "extract_metadata"},
    messages=messages
)
# Then process enrichment steps in a follow-up turn with tool_choice: "auto"

MCP Resources vs. Tools

MCP Tools
  • Execute actions — side effects, writes
  • Invoked by the model on demand
  • Example: create_issue, process_refund
MCP Resources
  • Read-only data catalogs — no side effects
  • Exposed as content for agent to consume
  • Reduces exploratory tool calls (e.g., database schema, issue summaries)

All tools from all configured MCP servers are discovered at connection time and available simultaneously. When choosing between a community MCP server and a custom one for standard integrations (e.g., Jira), prefer the existing community server — reserve custom servers for team-specific workflows.

Task 2.5
Built-in Tools: Read, Write, Edit, Bash, Grep, Glob
ToolPurposeWhen to Use
GrepSearch file contents for patternsFind all callers of a function, locate error messages, find imports
GlobMatch file paths by patternFind all *.test.tsx files, locate files by naming convention
ReadLoad full file contentWhen you need complete file context
WriteWrite full file contentCreating new files or full-file replacement
EditTargeted modification via unique text matchingPrecise edits when anchor text is unique
BashExecute shell commandsRunning tests, build tools, git operations
Edit Fallback Pattern

When Edit fails due to non-unique anchor text, fall back to Read the file first to understand its full content, then use Write to replace it reliably. Do not keep retrying Edit with the same anchor.

Efficient codebase exploration strategy

  • Start with Grep to find entry points and key functions — do not read all files upfront
  • Use Glob to locate relevant file groups (e.g., all test files)
  • Use Read to follow imports and trace flows incrementally
  • This "find then read" approach avoids context window exhaustion

Task 3.1
CLAUDE.md Configuration Hierarchy

Claude Code loads configuration from multiple levels simultaneously. Understanding which level to use for which type of instruction is a primary exam topic.

The three configuration levels

LevelLocationShared via Version Control?Use For
User~/.claude/CLAUDE.mdNo — user-onlyPersonal preferences, individual developer settings
Project.claude/CLAUDE.md or root CLAUDE.mdYes — everyone gets itUniversal team standards, build/test commands, coding conventions
DirectorySubdirectory CLAUDE.mdYes — in subdirectory scopeSubdirectory-specific overrides
Classic Exam Trap

A new team member is not receiving coding standard instructions. Root cause: the instructions were placed in the author's ~/.claude/CLAUDE.md (user-level) instead of the project-level .claude/CLAUDE.md. User-level config is never shared via version control.

@import syntax and .claude/rules/ modular organization

# In packages/api/CLAUDE.md
@import ../../.claude/rules/api-conventions.md
@import ../../.claude/rules/testing.md

# .claude/rules/ directory structure (alternative to monolithic CLAUDE.md)
.claude/
  rules/
    testing.md          # test file conventions
    api-conventions.md  # API handler patterns
    deployment.md       # deployment checklist
    security.md         # security rules

Use @import to selectively include relevant rule files per package. Use .claude/rules/ to split a monolithic CLAUDE.md into focused topic files. Use the /memory command to inspect which memory files are loaded and diagnose inconsistent behavior.

Task 3.3
Path-Specific Rules for Conditional Convention Loading

Rules in .claude/rules/ can be scoped to activate only when editing files matching specific glob patterns. This is more flexible than subdirectory CLAUDE.md files for conventions that span multiple directories.

---
# .claude/rules/testing.md
paths:
  - "**/*.test.tsx"     # all test files, anywhere in the codebase
  - "**/*.spec.ts"
---

All test files must use `describe`/`it` block structure.
Mock external dependencies with `jest.mock()`.
Test file must cover: happy path, error case, edge cases.
Minimum assertion density: 3 assertions per test.

Rules vs. subdirectory CLAUDE.md

.claude/rules/ with glob
  • Applies to files by type regardless of directory
  • Perfect for test files spread across the codebase
  • One rule file, loads conditionally
Subdirectory CLAUDE.md
  • Applies to files in that specific directory only
  • Cannot easily handle spread-out file types
  • Would require many CLAUDE.md files for test coverage
Exam Signal

Whenever a question involves "apply conventions to files spread across the codebase" — e.g., test files next to their source — the answer involves .claude/rules/ with glob patterns, not subdirectory CLAUDE.md files.

Task 3.4
Plan Mode vs. Direct Execution
ModeUse WhenExamples
Plan ModeComplex tasks, architectural decisions, large-scale changes, multiple valid approaches, multi-file modificationsMonolith → microservices, library migration (45+ files), choosing between integration approaches with different infrastructure requirements
Direct ExecutionSimple, well-scoped, single-file changes with a clear pathAdding a date validation check to one function, fixing a bug with a clear stack trace
Don't "discover" complexity — plan for known complexity

If the task is already stated to be complex (e.g., "restructure monolith into microservices"), do not use direct execution and switch to plan mode "if complexity emerges." The complexity is stated upfront — use plan mode from the start.

The Explore subagent

Use the Explore subagent to isolate verbose discovery output from the main conversation context. It handles investigation independently and returns only a structured summary — preserving the main session's context budget for implementation work.

Combining modes effectively

The most effective pattern for large tasks: use plan mode for exploration and architectural decision-making, then switch to direct execution for implementing the planned approach. This separates the expensive "understanding the codebase" phase from the "making changes" phase.

Task 3.5

When prose descriptions produce inconsistent results

If natural language instructions produce inconsistent output, switch to concrete input/output examples. Provide 2–3 transformations showing exactly what goes in and what comes out. This is more effective than refining the prose description.

Four refinement patterns

PatternWhenHow
I/O ExamplesProse instructions interpreted inconsistentlyShow 2-3 concrete input → output pairs
Test-DrivenImplementation tasksWrite test suite first; iterate by sharing test failures

Task 3.6
CI/CD Pipeline Integration

Non-interactive mode

# The -p flag is the ONLY documented way to run non-interactively
claude -p "Review this PR for security issues"

# Structured JSON output for machine parsing
claude -p "Analyze for bugs" --output-format json --json-schema ./schema.json
Exam Trap

Options like CLAUDE_HEADLESS=true, --batch, or stdin redirect from /dev/null are not real Claude Code flags. The only correct answer for non-interactive CI mode is the -p (or --print) flag.

CI/CD best practices

  • Use CLAUDE.md to provide project context (test standards, fixture conventions, review criteria) to CI-invoked Claude Code — it reads this file automatically
  • For PR re-reviews, always include prior review findings in context and instruct Claude to report only new or still-unaddressed issues to prevent duplicate comments
  • For test generation, provide existing test files in context to avoid suggesting scenarios already covered
  • Avoid using the same Claude session that generated code to review it — it retains reasoning context and is less likely to find its own mistakes. Use an independent review instance

Task 4.1
Designing Prompts with Explicit Criteria

Vague instructions ("be conservative," "only flag high-confidence findings") do not reduce false positives. They are interpreted inconsistently. Explicit criteria define exactly what to flag vs. skip.

❌ Vague Instruction
  • "Check that comments are accurate"
  • "Only report high-confidence issues"
  • "Be conservative in your findings"
✓ Explicit Criteria
  • "Flag comments ONLY when claimed behavior contradicts actual code behavior"
  • "Report: security vulnerabilities, data bugs. Skip: style, local patterns, minor naming"
  • "Severity HIGH = production-breaking; LOW = cosmetic"
False Positives Undermine Trust

A high false positive rate in one category (e.g., style comments flagged as bugs) causes developers to dismiss findings in all categories — including accurate security findings. If a category has persistently high false positives, temporarily disable it while improving its criteria, rather than letting it erode trust in the whole system.

Explicit severity criteria

Don't just say "classify severity." Provide concrete code examples for each severity level. This is the only way to achieve consistent classification across reviewers and sessions.

Task 4.2
Few-Shot Prompting

Few-shot examples are the most effective technique for achieving consistently formatted, actionable output when detailed instructions alone produce inconsistent results. They also help the model generalize to novel patterns — not just match pre-specified cases.

When to use few-shot examples

  • Output format is inconsistent despite clear prose instructions
  • Ambiguous cases require demonstrating the reasoning behind a choice
  • Extraction tasks where documents have varied structure (inline vs. bibliography citations)
  • Reducing false positives by showing examples of acceptable-but-not-flagged patterns

Best practices for few-shot examples

<examples>
  <example>
    <input>// Comment: "Returns null if user not found"
    return user ?? throw new Error("User not found");</input>
    <output>
    {
      "flag": true,
      "reason": "Comment says 'returns null' but code throws an exception",
      "severity": "HIGH",
      "category": "comment_mismatch"
    }
    </output>
  </example>
  <example>
    <input>// Returns user object or null
    return users.find(u => u.id === id) ?? null;</input>
    <output>
    {
      "flag": false,
      "reason": "Comment accurately describes the behavior"
    }
    </output>
  </example>
</examples>

Anthropic recommends 3–5 examples for most tasks: relevant to your use case, diverse (covering edge cases), and wrapped in <examples> XML tags so Claude distinguishes them from instructions. Include examples showing what NOT to flag alongside what to flag.

Task 4.3
Enforcing Structured Output via tool_use and JSON Schemas

Using tool_use with a JSON schema is the most reliable approach for guaranteed schema-compliant structured output. It eliminates JSON syntax errors entirely. However — this is critical for the exam — it does not prevent semantic errors.

The two types of errors — and what tool_use fixes

Error TypeExampleDoes tool_use fix it?
Syntax errorsMissing bracket, trailing comma, wrong typeYes — completely eliminated
Semantic errorsLine items that don't sum to total; value in wrong fieldNo — requires validation logic

Extraction tool pattern

tools = [{
    "name": "extract_invoice",
    "description": "Extract structured invoice data from document",
    "input_schema": {
        "type": "object",
        "properties": {
            "vendor": {"type": "string"},
            "total": {"type": "number"},
            "currency": {
                "type": "string",
                "enum": ["USD", "EUR", "GBP", "other"]
            },
            "currency_detail": {           # for "other" — extensible enum pattern
                "type": ["string", "null"]
            },
            "payment_terms": {             # nullable — may not exist in every doc
                "type": ["string", "null"]
            }
        },
        "required": ["vendor", "total", "currency"]
    }
}]

# Use "any" when document type unknown — guarantees a tool is called
response = client.messages.create(
    tools=tools,
    tool_choice={"type": "any"},
    messages=messages
)

Schema design principles

  • Nullable optional fields: Fields that may not exist in source documents should be ["string", "null"]. If they're required without nullable, the model will fabricate values to satisfy the schema.
  • Extensible enums: Use "other" in the enum + a separate X_detail string field for values outside the predefined set.
  • "unclear" for ambiguous cases: Add "unclear" as an enum value rather than forcing the model to pick when it can't determine the right value.

Semantic validation with Pydantic

tool_use eliminates syntax errors. But semantic errors — wrong values, misplaced data, business logic violations — require a separate validation layer. Pydantic is the standard tool for this in Python.

from pydantic import BaseModel, validator, ValidationError
from typing import List, Optional

class LineItem(BaseModel):
    description: str
    quantity: int
    unit_price: float
    line_total: float

    # Semantic validator: line_total must equal quantity × unit_price
    @validator("line_total")
    def validate_line_total(cls, v, values):
        expected = values["quantity"] * values["unit_price"]
        if abs(v - expected) > 0.01:
            raise ValueError(ff"line_total {v} ≠ qty×price {expected}")
        return v

class Invoice(BaseModel):
    vendor: str
    line_items: List[LineItem]
    stated_total: float
    calculated_total: Optional[float] = None  # computed, not extracted

    # Semantic validator: sum of line items must match stated_total
    @validator("stated_total")
    def validate_stated_total(cls, v, values):
        if "line_items" in values:
            calc = sum(i.line_total for i in values["line_items"])
            if abs(v - calc) > 0.01:
                raise ValueError(ff"stated_total {v} ≠ line items sum {calc}")
        return v

# Attempt extraction + semantic validation
try:
    invoice = Invoice(**extracted_tool_data)
    # Success — schema AND semantic checks passed
except ValidationError as e:
    # e.errors() gives specific field-level failure messages
    # Pass these to retry-with-feedback loop
    retry_with_errors(document, extracted_tool_data, e.errors())
tool_use vs Pydantic — What Each Solves

tool_use JSON schema: eliminates syntax errors (wrong type, missing required field, extra properties). Pydantic validators: catches semantic errors (values that are individually valid but logically inconsistent together). You need BOTH for production-grade extraction.

Anthropic now offers native Structured Outputs (generally available) which uses constrained decoding to guarantee JSON schema compliance directly — no tool_use workaround needed. Use the output_config parameter with a JSON schema. Both approaches are in-scope; tool_use is the pattern the exam was designed around, but knowing the newer native approach is valuable context.

Task 4.4
Validation, Retry, and Feedback Loops

Retry-with-error-feedback pattern

def extract_with_retry(document, max_retries=3):
    for attempt in range(max_retries):
        result = call_extraction_tool(document)

        errors = validate(result)
        if not errors:
            return result

        # On retry: include original document + failed extraction + specific errors
        # DO NOT just re-send the same prompt — include what failed and why
        messages.append({
            "role": "user",
            "content": f"""
The previous extraction had these validation errors:
{errors}

Please re-extract from the original document, correcting these specific issues.
Original document: {document}
Failed extraction: {result}
"""
        })
    raise ExtractionError("Max retries exceeded")

When retries will vs. won't help

Retry will help
  • Format mismatch (date format wrong, number as string)
  • Field placed in wrong location in output
  • Structural output errors the model can self-correct
Retry won't help
  • Required information simply absent from source document
  • External document referenced but not provided
  • Information requires domain knowledge not in context

Self-correction validation patterns

  • Extract calculated_total alongside stated_total — flag discrepancies automatically
  • Add conflict_detected boolean when source data contains contradictions
  • Add detected_pattern field to structured findings to enable systematic analysis of which code patterns cause false positives when developers dismiss findings
Task 4.5
Batch Processing with the Message Batches API

Key facts about the Message Batches API

  • Cost: 50% savings vs. synchronous API
  • Processing time: up to 24 hours (no guaranteed latency SLA)
  • Multi-turn tool calling: NOT supported within a single batch request
  • Correlation: use custom_id on each request to match responses

When to use batch vs. synchronous

WorkflowAPI ChoiceReasoning
Blocking pre-merge checkSynchronousDeveloper waits for result; cannot tolerate 24hr delay
Overnight technical debt reportBatchNon-blocking; reviewed next morning; 50% cost savings
Weekly compliance auditBatchLatency-tolerant; high volume; cost matters
Nightly test generationBatchRuns overnight; results ready for morning review
SLA Calculation Pattern

If you need a 30-hour SLA with batch processing taking up to 24 hours, you must submit batches at least every 6 hours (30h SLA − 24h max batch = 6h submission window). The exam guide also references a 4-hour submission window for tighter SLAs — know the formula: submission window = SLA − 24h max processing.

Prompt refinement before batch submission

Before batch-processing a large volume of documents (e.g., 10,000 invoices), always run prompt refinement on a small representative sample first — typically 20–50 documents. This lets you catch systematic extraction errors and fix the prompt before committing to the full batch cost. Iterating after a 10,000-document batch is far more expensive than fixing before it.

Sample First, Then Scale

The exam-tested workflow: (1) select a stratified sample covering all document types in your corpus, (2) run extraction and measure accuracy per document type and per field, (3) fix any systematic errors via prompt or schema changes, (4) only then submit the full batch. Skipping the sample step is the anti-pattern.

Failure handling by custom_id

# Re-submit only failed documents — don't resubmit the whole batch
for result in batch_results:
    if result.error:

        if result.error.type == "context_window_exceeded":

            resubmit_as_is(original)
Task 4.6
Multi-Instance and Multi-Pass Review Architectures

Self-review limitation

When a model reviews code it just generated within the same session, it retains the reasoning context from generation. This makes it less likely to question its own decisions. An independent review instance — without the generation context — is significantly more effective at catching subtle issues.

Multi-pass architecture for large reviews

Pass 1–N: Per-file local analysis — Review each file individually for logic bugs, security issues, local correctness. Consistent depth guaranteed.
↓
Pass N+1: Cross-file integration — Review data flow across file boundaries, interface contracts, shared state, contradictions between files.
Larger Context Window ≠ Better Attention

A larger context window does not solve attention quality issues. Processing 14 files at once still results in diluted, inconsistent attention — some files get detailed analysis while others get superficial comments. The fix is architectural (per-file passes), not a larger model.

Confidence-based routing

Have the model self-report confidence alongside each finding. Use calibrated thresholds (set against a labeled validation set) to route low-confidence findings to human review. High-confidence findings can go directly to the developer. This makes limited reviewer capacity more effective.

Task 5.1
Managing Conversation Context for Long Interactions

The "lost in the middle" effect

Models reliably process information at the beginning and end of long inputs, but can miss findings from middle sections. For large aggregated inputs: place key findings summaries at the beginning, organize detailed results with explicit section headers, and don't rely on middle-positioned content for critical information.

Progressive summarization risks

When summarizing long conversations to reduce context, specific values get lost. Never summarize away: amounts, dates, order numbers, customer-stated expectations, specific error messages. These must be extracted into a persistent "case facts" block that travels with every prompt separately from the summarized narrative.

Tool output trimming

# A customer lookup might return 40+ fields
# Only keep the 5 fields relevant to the current task
def trim_order_result(full_order):
    return {
        "order_id": full_order["order_id"],
        "status": full_order["status"],
        "items": full_order["items"],
        "return_eligible": full_order["return_eligible"],
        "return_window_expires": full_order["return_window_expires"]
        # Drop: shipping_carrier, warehouse_id, internal_flags, etc.
    }

Verbose tool outputs accumulate in context and consume tokens disproportionately to their relevance. Trim at the source before appending to conversation history.

Upstream agents and downstream context budgets

When downstream agents have limited context budgets (e.g., a synthesis agent receiving output from 6 search subagents), instruct upstream agents to return structured summaries instead of verbose content and reasoning chains. Each subagent should return: key facts, citations, relevance scores — not full document transcripts plus its reasoning process. This is a structural fix: the upstream agent's output format must be designed with the downstream agent's budget in mind.

# Bad — upstream returns verbose content + reasoning
"content": "I found this article about AI adoption... The author argues... 
This is relevant because... The methodology was... In conclusion..."

# Good — upstream returns structured summary for downstream budget
{
  "claim": "Global AI adoption in creative industries grew 340% in 2024",
  "source_url": "https://example.com/report",
  "source_name": "McKinsey Global AI Report 2024",
  "publication_date": "2024-11-15",
  "relevance_score": 0.92,
  "key_excerpt": "340% growth driven primarily by generative tools..."
}

The /compact command

In extended Claude Code sessions, use /compact to reduce context usage when the context window fills with verbose discovery output. This compresses conversation history while preserving key findings.

Task 5.2
Escalation and Ambiguity Resolution Patterns

When to escalate immediately — no exceptions

  • Customer explicitly requests a human agent — honor this immediately, do not first attempt to resolve
  • Policy is ambiguous or silent on the customer's specific request (e.g., competitor price matching when policy only covers own-site adjustments)
  • Agent cannot make meaningful progress after attempting resolution

When NOT to escalate immediately

  • Customer is frustrated but the issue is within the agent's capability — acknowledge frustration, offer resolution, escalate only if they reiterate preference for a human
  • Case is merely "complex" — complexity alone is not an escalation trigger; assess whether the agent can make progress
Unreliable Escalation Proxies

Neither sentiment analysis nor self-reported confidence scores are reliable proxies for case complexity. An agent can be confidently wrong on hard cases. Sentiment does not correlate with complexity. Use explicit policy-based criteria with few-shot examples instead.

Multiple customer matches

When a lookup returns multiple customer matches, the agent must ask for additional identifiers — it must not use heuristics to select among matches. Any heuristic selection risks operating on the wrong customer's account.

Task 5.3
Error Propagation in Multi-Agent Systems

The two anti-patterns

  • Silent suppression: subagent catches an error and returns empty results as "success" — the coordinator has no way to know the search failed and makes decisions on incomplete data
  • Wholesale termination: a single subagent failure propagates as an exception that terminates the entire workflow — all other subagents' successful work is discarded

The right pattern: structured error context

# Subagent should return this on failure, not raise an exception
return {
    "status": "partial_failure",
    "failure_type": "search_timeout",
    "attempted_query": original_query,
    "partial_results": results_before_timeout,   # Whatever we got
    "alternatives_available": ["try_cached_results", "narrow_query"],
    "recommended_action": "retry_with_narrower_query"
}

The coordinator can then decide: retry with a modified query, use partial results with a coverage annotation, or proceed acknowledging the gap. This is impossible with a generic "search unavailable" status.

Coverage annotations in synthesis

When synthesis output is based on incomplete data due to subagent failures, the synthesis agent must annotate which findings are well-supported vs. which topic areas have gaps due to unavailable sources. This preserves intellectual honesty in the final report.

Task 5.4
Context Management in Large Codebase Exploration

Context degradation in extended sessions

As a session grows, models start referencing "typical patterns" rather than specific classes discovered earlier. Signs of degradation: inconsistent answers to the same question, loss of specifics from earlier in the session, reverting to generic responses.

Scratchpad files as external memory

# Pattern: agent writes findings to a file as it discovers them
# This survives context window compaction
Write("claude-findings.md", f"""

- Session store: Redis, 24h TTL

- ORM: TypeORM 0.3.x
- Connection pool: max 20 connections
...
""")

Crash recovery with structured state exports

Design long-running agents to export structured state to a manifest file after each major phase. If the session crashes or needs to be resumed, the coordinator loads the manifest and injects it into agent prompts, avoiding full re-exploration.

Task 5.5
Human Review Workflows and Confidence Calibration

The aggregate accuracy trap

A 97% overall accuracy metric can mask catastrophic performance on specific document types or fields. A system that's 99.9% accurate on simple invoices but 60% accurate on multi-currency international invoices needs targeted improvement — and the aggregate metric hides this.

Confidence calibration workflow

  1. Model outputs field-level confidence scores alongside each extraction
  2. Build a labeled validation set by having humans review a representative sample
  3. Calibrate confidence thresholds against the labeled set (what score reliably predicts correct extraction?)
  4. Route extractions below threshold to human review
  5. Continuously run stratified random sampling to detect novel error patterns and threshold drift
Stratified Sampling

Don't sample randomly from all extractions — sample by document type, field, and confidence band. This detects systematic errors in specific segments that would be invisible in a flat random sample.

Task 5.6
Information Provenance in Multi-Source Synthesis

How attribution is lost

When a subagent summarizes findings without preserving source attribution, the claim-to-source link is permanently severed. The synthesis agent cannot reconstruct it from a prose summary. Subagents must output structured claim-source mappings from the start.

Structured claim-source format

# What subagents MUST return (not prose summaries)
{
  "claim": "Global AI adoption in creative industries grew 340% in 2024",
  "source_url": "https://example.com/report",
  "source_name": "McKinsey Global AI Report 2024",
  "excerpt": "...relevant passage verbatim...",
  "publication_date": "2024-11-15",  # REQUIRED for temporal interpretation
  "confidence": "high"
}

Handling conflicting sources

When two credible sources report different statistics, the synthesis agent must not arbitrarily pick one. It must preserve both values with source attribution and annotate the conflict. The coordinator decides how to reconcile before the report is finalized.

❌ Wrong
  • "AI adoption grew 340% (McKinsey)"
  • Silently drops the conflicting Bloomberg figure of 180%
✓ Correct
  • "AI adoption grew 340% (McKinsey, Nov 2024) or 180% (Bloomberg, Dec 2024) — conflict detected, see sources"

Why publication dates are mandatory

Without publication dates, statistics from different years may appear contradictory when they're actually showing a temporal trend. Include dates in structured output so downstream agents can determine whether a "conflict" is actually a time-series progression.

Rendering content types appropriately in synthesis

Synthesis agents must not convert all content to a uniform format. Different content types have different optimal representations, and flattening them loses information structure:

Content TypeCorrect RenderingWhy
Financial data, statistics, comparisonsTablesReaders need to scan and compare values; prose buries numbers
News, narrative findings, qualitative analysisProse paragraphsSequential reasoning flows naturally; tables would fragment it
Technical findings, bugs, security issuesStructured listsEach item is discrete and actionable; prose obscures individual items
Mixed well-established vs contested findingsDistinct labeled sectionsReader must know confidence level; mixing them is misleading
Exam Signal

When a question asks how synthesis output should be structured, look for answers that preserve the original content type — not answers that convert everything to one format (all prose, all tables, all bullets). The exam tests whether you know that format choice is meaningful, not cosmetic.

Batch API has up to 24-hour processing time with no guaranteed latency SLA — unsuitable for blocking pre-merge checks where developers wait. It's ideal for the overnight technical debt report. B is wrong because "often faster" isn't acceptable for blocking workflows. C is a misconception — batch results can be correlated via custom_id. D adds unnecessary complexity when the simpler answer is matching each API to its appropriate use case.

Question 12 · D4

A pull request modifies 14 files across the stock tracking module. Your single-pass review produces inconsistent results: detailed feedback for some files, superficial comments for others, obvious bugs missed, and contradictory feedback — flagging a pattern as problematic in one file while approving identical code elsewhere. How should you restructure the review?

A ✓ Split into focused passes: analyze each file individually for local issues, then run a separate integration-focused pass examining cross-file data flow.
B ✗ Require developers to split large PRs into smaller submissions of 3–4 files before the automated review runs.
C ✗ Switch to a higher-tier model with a larger context window to give all 14 files adequate attention in one pass.
D ✗ Run three independent review passes on the full PR and only flag issues that appear in at least two of the three runs.
Why A is correct

Splitting into focused passes directly addresses attention dilution — the root cause of inconsistent results. File-by-file analysis ensures consistent depth; a separate integration pass catches cross-file issues. B shifts burden to developers without improving the system. C misunderstands that larger context windows don't solve attention quality issues. D would suppress detection of real bugs by requiring consensus on issues that may only be caught intermittently.
